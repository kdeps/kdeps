# Single Go Context - From Entry Point, Created Once, Reused

## Goal

A single root `context.Context` created at the entry point of the agent loop
(`runAgentLoopCmd` in `cmd/serve.go`). All derived contexts derive from it.
No `context.Background()` calls below the entry point.

---

## Status

**Phase 1 (agent loop critical path) — COMPLETE** (Oct 2025 — Jul 2026)

All phases complete. ~60 Background() calls remain in leaf/exported functions where Background() is the correct root.

---

## The Problem

**~120 call sites** of `context.Background()` across the agent loop path and
executor packages. No single root. No context propagation.

### Root: no context at all

`main.go` and `cmd/root.go` -- zero context usage. The entry point
`runAgentLoopCmd` (in cmd/serve.go) creates `context.Background()` once as the
canonical root and passes it down.

### 5. cmd/ subcommands (Phase 5 -- COMPLETE - intentionally skipped)

Standalone CLI commands, not agent loop. Each could create its own root but
this is lower priority -- they start and exit quickly.

**Phase 5 decision**: All 29 `context.Background()` calls in `cmd/` subcommands
are intentional. They fall into three categories:

1. **Entry-point root contexts** (most): Each `cmd/*.go` command handler is a
   standalone entry point that starts and exits within seconds. Creating a
   `context.Background()` as the root is correct — there is no parent context
   to inherit. Adding a `signal.NotifyContext` wrapper is a separate concern
   (signal handling), not a context-propagation task.

2. **Standalone helper functions** (some): Functions like `CheckPortAvailable`,
   `warmupLlamafiles`, `fetchReadmeURL` are called from multiple entry points
   and don't receive a context parameter. Adding one would require changing
   public function signatures for no benefit.

3. **Goroutine dispatches** (a few): `botDispatcherRunFunc(context.Background(), ...)`
   launches a long-running background loop — Background() is the appropriate
   parent since the goroutine outlives the caller.

**Verdict**: Phase 5 needs no code changes. 0 of the 29 are fixable without
changing exported APIs or adding unnecessary signal plumbing.

## Why ExecutionContext doesn't help

Every executor receives `*executor.ExecutionContext` (pkg/executor/context_types.go:31),
which does NOT carry a Go `context.Context` anywhere. It has fields for workflow,
resources, memory, etc. but no `Ctx context.Context` field.

So each executor that makes an HTTP call, a DB query, or spawns a process
must create its own `context.Background()`. Adding a `Ctx` field to
`ExecutionContext` would let all executors inherit the root context.

## Desired Flow (agent loop) -- DONE

```
main.go (no context)
  -> cmd.Execute()
    -> cmd/root.go RunE
      -> runAgentLoopCmd (serve.go)
         |
         |  rootCtx, rootCancel := context.WithCancel(context.Background())
         |  defer rootCancel()
         |
         |-- agent.RegisterBuiltinTools(rootCtx, registry)
         |-- prefetchCtx = signal.NotifyContext(rootCtx, ...)
         |-- repl := agent.NewREPL(loop, rootCtx)
         |       loopCtx = context.WithCancel(rootCtx)
         |       turnCtx = context.WithCancel(loopCtx)
         |-- repl.Run()
```
